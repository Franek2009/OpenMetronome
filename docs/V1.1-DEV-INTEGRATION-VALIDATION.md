# DEV — integracja i kwalifikacja pełnego toru

## Zakres

Wariant DEV rejestruje każdą sesję: planowane sloty PCM (także ciszę, akcenty,
podziały i odliczanie), konfigurację, renderowanie i zapisy sinka, status i błędy,
focus/noisy, cykl usługi/tło oraz UUID historii i wyniki checkpointów.
Raporty ZIP w Ustawieniach DEV mają cztery pliki: beats.csv, events.csv,
audio.csv, metadata.json. PROD nie zawiera implementacji tego magazynu.

Zapis IO jest asynchroniczny, transport ma 4 MiB łącznie, dysk 512 MiB/sesję
oraz 2 GiB łącznie. Limity, brak miejsca i uszkodzenia są jawnie raportowane.
Nie kasujemy starych raportów automatycznie. Błąd diagnostyki nie zatrzymuje audio.
Prefiks sprzed Start ma 32 miejsca; jego utrata również jest uwzględniana.

Znaleziony dodatkowy błąd cyklu życia: asynchroniczny Stop mógł pozostawić
finalizator z nieterminalnym snapshotem. Finalizator aplikacji czeka na końcowy
stan **silnika**, także po zniszczeniu relay kontrolera. Limit 10 sekund oznacza
awaryjny zapis przerwanej sesji i komunikat, nie nieskończoną rezerwację.
Test wymusza późniejszy końcowy snapshot (2 s zamiast 1 s) i zablokowany zapis.

## Protokół ART offline

`DevDiagnosticsQualificationTest`: rzeczywisty PcmAudioEngine, priorytet audio,
TraceSessionStore, konsument IO i strumieniowy eksport; sink i focus są atrapami.
Nie tworzy AudioTrack, nie emituje dźwięku ani wibracji. Bazowy/DEV/bazowy,
każda próba 3000 bloków rozgrzewki i 3000 pomiaru, 48 kHz / 256 ramek,
137 BPM, 4/4, podział pojedynczy, głośność konfiguracji 100%.
Odniesienie to niższe bazowe p99. Zegar pomiaru to CPU bieżącego wątku.
Pomiar p99 całej ścieżki renderowania obejmuje także dodanie rekordu RENDER.
Wymagamy identycznego PCM w trzech próbach, wszystkich planowanych BEAT,
zerowych strat obu kanałów i kompletnego eksportu powiązanego z historią.
Budżet wzrostu p99 renderowania: 10%; p99 pracy bloku < połowy jego czasu.

Wstępna lokalna kwalifikacja przed aktywacją (roboczy kod na rodzicu 9ad9b59;
czas samego renderowania przed dodaniem RENDER):

| 26 | 323160 ns | 325057 ns | 1,0059 | identyczny / 0 |
| 35 | 286434 ns | 284559 ns | 0,9935 | identyczny / 0 |

Obie próby **PASS**. SHA-256 przyjętego PCM:
`09ce5739fe85299b38b30f4f78a7851be80a8377f5a364099ce6f47dffa7a901`.
Niższy wynik DEV nie jest dowodem przyspieszenia: to pomiar emulatora z szumem.
Końcowe CI mierzy szerszą ścieżkę (łącznie z dodaniem RENDER) i powtarza kwalifikację dla dokładnego HEAD; JSON jest artefaktem
`quiet-emulator-report-api26/35`, z sourceRevision, pomiarami i jawnymi null
fizycznego jittera/latencji. Lokalny rodzic nie jest udawany jako końcowy SHA.

Próbkowanie heap/PSS co 250 ms nie wyznacza ścisłego maksimum ani przyczynowej
różnicy między wariantami. 4 MiB ogranicza transport, nie cały proces.
Scenariusz nie dowodzi braku strat przy wszystkich obciążeniach i urządzeniach.
Przeciążenia/dysk/restart/CRC/overflow są badane osobnymi testami błędów.

## Wyniki i granice

- JVM i kompilacje obu debug flavorów oraz instrumentacji: PASS przed aktywacją.
- Kwalifikacja ART API26/35: PASS; wcześniejsza kompilacja testu FAIL (PSS Long),
  naprawiona i ponowiona. Błędna nazwa runnera w pojedynczym poleceniu nie
  uruchomiła testu; poprawne uruchomienie dało powyższy wynik.
- Test zniszczenia usługi i wymuszonego startForeground failure: lokalnie PASS.
- Pełne CI, Lint i inspekcję obu release potwierdzamy w PR dla jego dokładnego HEAD.
- Fizyczne audio/wibracje: NIE WYKONANO. Nie są oznaczane jako PASS.
- Jitter i latencja fizycznego wyjścia: NIEZMIERZONE.

Sześć dawnych testów sprzętowego audio usunięto na życzenie użytkownika.
Pozostały zabezpieczenia runnera, testy ich działania oraz testy PCM/atrap.
Odbiór sprzętowy jest manualną checklistą użytkownika, nie pominiętym PASS.

# Weryfikacja propozycji 1.0.0-rc.1

Stan: prace na `fix/rc1-stabilization`, bez scalenia, tagu i publikacji.
Punkt odniesienia: opublikowane `v0.13.0-beta.3`.
Kandydat: versionCode 16, versionName 1.0.0-rc.1, `org.openmetronome`.
Schemat Room 2 i format `.ombak` v1 pozostają bez zmian.

## Wstępny audyt i reprodukcje

- **P1 foreground — potwierdzone:** po rezerwacji wyjątek z `startForeground()`
  trafiał do `endForeground()`, którego strażnik `!foreground` pomijał cleanup.
  Rezerwacja mogła blokować Start i backup do zniszczenia usługi.
- **P1 zapis sesji — potwierdzone:** `finally` w SessionRecorder oznaczało sesję
  jako zamkniętą nawet po błędzie transakcji. Test JVM ponowienia tego samego
  terminalnego stanu najpierw FAIL (brak drugiej próby), po poprawce PASS.
- **P1 zniszczenie usługi — potwierdzone w kodzie:** scope obsługujący finalizację
  był anulowany w `onDestroy()`, a blokada zwalniana bez oczekiwania na zapis.
- **P2 niespójne dane pochodne — potwierdzone:** poprawnie zbudowany ZIP mógł
  zawierać inne dni/czas checkpointu niż sesja. Istniejące fixture'y mają takie
  rozbieżności; nie odrzucamy ich z tego powodu.
- **Nie potwierdzono błędu podziału dni w PracticeTimeline:** dostępne testy
  pokrywają północ oraz 23/25-godzinny dzień zmiany czasu. Ryzykiem były
  niezależne dane archiwum i nieograniczony koszt ich rekonstrukcji.
- **Odrzucono rozwiązanie polegające na ścisłym odrzucaniu historycznych
  checkpointów/dni:** łamałoby zgodność poprawnie wydanych archiwów v1.

## Zastosowane rozwiązania

Rezerwacja jest śledzona niezależnie od flagi foreground i zwalniana po
finalizacji także przy nieudanej promocji usługi. Promocja już związanej
usługi następuje przed `startForegroundService()`, aby wyjątek nie zostawiał
aktywnego systemowego timeoutu foreground. Nieaktualne tokeny Start są
odrzucane przed zmianą stanu nowszego żądania. Finalizacja jest skończonym
zadaniem należącym do AppData, poza anulowanym scope usługi. Zniszczenie usługi
zatrzymuje silnik i przekazuje terminalny stan do tego samego rejestratora.

Każdy checkpoint trafia do prywatnej kolejki zapisu: plik tymczasowy, fsync,
atomowa podmiana i synchronizacja katalogu poprzedzają transakcję Room.
Plik jest usuwany po zatwierdzeniu i synchronizacji bazy. Ponowienie używa
tego samego ID sesji i transakcyjnie zastępuje jej dni, bez duplikowania sesji.
Restart odzyskuje pliki kolejki; niedokończone sesje oznacza jako przerwane.
Błąd odzyskiwania zachowuje materiały i pozwala na późniejsze ponowienie.

Przy błędzie dysku sesja zostaje w kolejce, aplikacja zgłasza błąd i zwalnia
rezerwację odtwarzania. Kolejne checkpointy oraz eksport/import ponawiają
zaległe zapisy. Eksport CSV i `.ombak` nie otwierają dokumentu docelowego,
jeśli zapis zaległych sesji nadal się nie udaje. CSV wymaga zakończenia sesji.
Nie stosujemy nieskończonej pętli ponowień ani blokowania wątku głównego.

Publiczny import/eksport `.ombak` rekonstruuje `checkpointAt` i dni z
`startedAt`, `durationMs` i `zoneId`. Zachowuje ID, czas trwania, konfigurację,
flagi sesji, presety oraz sample. Nadal odrzuca uszkodzoną strukturę,
osierocone/zdublowane dni i wartości ujemne, których wcześniejszy parser
również nie akceptował. Rekonstrukcja ma limit 100 000 rekordów dni na
archiwum i kontrolę przepełnienia czasu. Prywatny dziennik restore używa
odczytu/zapisu bez normalizacji, aby cofać dokładne poprzednie dane.

### Nieudane przebiegi pośrednie

- Reprodukcja JVM starego błędu finalizacji: 1 test FAIL, oczekiwany wynik
  przed poprawką. Kolejna regresja wykryła pomijanie kontroli osieroconych
  dni podczas normalizacji; kontrola przywrócona, końcowe 144 JVM PASS.
- Pierwsze ciche przebiegi API 26 i 35: po 32 PASS, następnie crash procesu
  z `ForegroundServiceDidNotStartInTime`. Ujawniły, że samo `stopSelf()`
  związanej usługi nie usuwa obowiązku promocji po nieudanym
  `startForeground()`. Poprawiono kolejność; powtórzone pełne zestawy PASS.
  Zachowane raporty: `app/build/reports/rc1/failed-first/`.
- Pierwszy lokalny start emulatora API 26 z `-gpu software`: brak działających
  poleceń shell ADB mimo sygnału boot complete. Bez deklaracji PASS;
  emulator uruchomiony ponownie z `swiftshader_indirect`. API 35 używa software.
  Nie zmieniano ani nie czyszczono danych aplikacji użytkownika.

## Manualne potwierdzenie użytkownika

Zgłoszenie z 2026-11-01: około godzinna praktyka na kontrabasie bez zauważonych
przerw lub problemów utrudniających ćwiczenie. Telefon był również używany
z zablokowanym ekranem, przez nieustalony czas. Import własnego sampla i jego
odsłuch poprawne, bez zauważonych trzasków i nierówności. Trening wyciszeń
oraz zmian tempa sprawdzany wcześniej i zgłoszony jako działający.

Wersja użytego APK niepotwierdzona. To relacja użytkownika, bez instrumentacji,
liczników underrunów i pomiaru jittera. Nie jest wynikiem testu nowego RC.
[Pełny kontekst M6](M6-ACCEPTANCE.md).

## Ograniczenia i ryzyka

- Jeśli dysk odrzuca zarówno plik odzyskiwania, jak i bazę, najnowsza migawka
  pozostaje wyłącznie w pamięci. Zabicie procesu przed udanym ponowieniem
  może ją utracić. Nie deklarujemy niemożliwej gwarancji zapisu na pełnym dysku.
- Uszkodzony plik kolejki pozostaje zachowany i blokuje eksport do czasu
  odzyskania danych; Start nie jest z tego powodu trwale zarezerwowany.
- Nagłe zabicie procesu może utracić fragment po ostatnim trwałym checkpointcie.
  Próby zniszczenia Service i ponownego otwarcia magazynu nie są fizycznym
  odcięciem zasilania urządzenia.
- Normalizacja poprawia dane pochodne archiwum; nie zgaduje innej długości
  sesji, jeżeli samo źródłowe `durationMs` było historycznie błędne.
- Fizyczny jitter, latencja wyjścia i underruny podczas ręcznej sesji:
  **niezmierzone**. Wibracje: brak nowego odbioru. Lenovo: pominięte decyzją
  użytkownika. Nie uruchamiano automatycznego audio/wibracji na telefonach.
- Ostatnio odczytana zwykła instalacja Samsunga ma podpis niezgodny z
  oficjalnym. Nie odinstalowano aplikacji, nie usuwano danych i nie obchodzono
  sprawdzania podpisu. Osobno pozostaje bezpieczna ścieżka jej aktualizacji.
- Test aktualizacji na emulatorach używa kopii APK podpisanych jednorazowym
  kluczem testowym; nie zastępuje kontroli oficjalnego podpisanego artefaktu.

## Kryteria dopuszczenia stabilnego 1.0

1. Krytyczne regresje zapisów, foreground, backup/restore, migracji i aktualizacji
   zaliczone na zamrożonym kodzie; brak otwartych P1 i nieoczekiwanych pominięć.
2. JVM, Lint i wszystkie trzy APK PASS. Ciche API 26/35 PASS; audio SKIPPED
   opisane osobno. Produkcyjny APK pozbawiony komponentów debug/test.
3. Po osobnej zgodzie: podpisany RC zweryfikowany tym samym oficjalnym
   certyfikatem i rosnącym versionCode, z próbą aktualizacji zachowującą dane.
4. Manualny odbiór przypisany do znanej wersji RC: zwykła dłuższa praktyka,
   Start/Stop, blokada ekranu, Stop z powiadomienia i obsługa przerwania audio
   bez samoczynnego wznowienia. Potwierdzić poprawny zapis czasu sesji.
5. Zamknąć lub jawnie zaakceptować pozostałe punkty M6, w tym zakres odsłuchu
   treningu i decyzję o odbiorze wibracji. Brak pomiaru fizycznego jittera
   pozostaje jawnym ograniczeniem; nie jest zastępowany wymyślonymi wynikami.
6. Udokumentować zgodność podpisów i ochronę danych przy aktualizacji.
   M6 oraz stabilne 1.0 wymagają końcowego przeglądu i zgody użytkownika.

## Rekomendacja

**RC gotowy jako propozycja do osobnego zatwierdzenia procesu wydawniczego.**
Krytyczne poprawki i końcowa regresja przeszły. Nie jest to gotowość stabilnego
1.0 ani ukończenie M6. Przed dystrybucją należy zweryfikować podpisany
artefakt i aktualizację oficjalny→oficjalny; następnie odebrać znaną wersję RC
w zwykłej praktyce według kryteriów powyżej.

Nie scalono gałęzi do main, nie utworzono tagu i nie opublikowano APK.
Nie zmieniono certyfikatu ani identyfikatora aplikacji. Nie używano oficjalnego
klucza do lokalnych testów i nie usuwano danych użytkownika.
